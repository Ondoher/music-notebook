# Build System

## Purpose

Capture how the current Polylith build system works at a practical level for `music-notebook`.

This note is about:

- app build definitions
- feature inclusion
- build-time versus runtime responsibilities
- assets and CSS
- synthetic modules
- frontend test builds

This note is based on the current Polylith line used by repos such as `modmod`.
It is not a description of Polylith 2.0.

## Core Model

In Polylith, the build system is responsible for assembling the application out of:

- an app entrypoint
- included features
- copied assets
- CSS resources
- generated synthetic modules
- optional test entrypoints

The important philosophy is that application composition is explicit.

Files existing in the repo do not automatically become part of the app just because they are present.
They become part of the app because the build includes them.

## App Builds

An app build defines the top-level shape of a runnable application.

Typical app-build concerns are:

- app name
- source entrypoint
- output destination
- HTML template
- included features
- copied resources
- copied CSS
- optional test entrypoint
- optional test destination
- optional router module

In the current Polylith line, this can be defined in code or config.

Important consequence:

- if something exists in source but not in the app, the first place to check is the app build definition

## Build-Time Versus Runtime

One of the most important Polylith distinctions is:

- build-time decides what is included
- runtime decides what gets instantiated and used

That means there are two separate gates:

1. build inclusion
2. runtime activation

A feature can fail to appear for either reason:

- it was never included in the app build
- it was included in the build, but its runtime import/registration path is broken

This distinction matters a lot when debugging.

## Features In The Build

Features are build-time units of isolation and contribution.

A feature can contribute:

- source code
- config
- CSS
- resources
- loadables
- tests

The app build includes features explicitly.

Important consequence:

- feature inclusion is intentional, not automatic

This is part of what makes Polylith feature boundaries meaningful.

## Feature Build Files

Feature-local build files describe what a feature contributes to the final app.

Typical concerns in a feature build file are:

- `index`
  - the feature entrypoint
- `config`
  - feature-provided configuration
- `css`
  - feature-local shipped CSS
- `resources`
  - feature-local copied images or other non-code assets
- `loadables`
  - dynamically loaded feature modules

Practical consequence:

- putting a file next to a component is not enough if it must be copied into built output
- feature-local shipped assets need to be part of the feature build contribution

## Assets And CSS

Polylith treats copied assets as a first-class build concern.

Important categories are:

- app-wide resources
- app-wide CSS
- feature-local resources
- feature-local CSS

The common pattern is:

- assets that must physically exist in built output should live under the relevant asset paths used by the build
- CSS that is meant to ship with the app should be part of the asset flow rather than treated as incidental local source

Practical implication:

- asset placement is part of the build contract, not just file organization

## Templates

The build also owns HTML template expansion.

The template provides placeholders for generated content such as:

- CSS link tags
- top-level script tags

So the build is not only bundling JavaScript. It is also producing the HTML shell that points at the built output.

## Synthetic Modules

One of the most distinctive mechanics in Polylith is the use of synthetic modules.

These are modules generated by the build rather than existing as ordinary source files.

Important examples are:

- `@polylith/features`
- `@polylith/config`
- `@polylith/loader`

### `@polylith/features`

This synthetic module imports the entrypoints of all features included in the app build.

Practical consequence:

- importing `@polylith/features` is how the app gains the included feature code
- if a feature is not included in the build, it will not appear through this module

### `@polylith/config`

This synthetic module exposes configuration data assembled during the build.

Practical consequence:

- runtime config access is fed by build-time config aggregation

### `@polylith/loader`

This synthetic module supports named dynamic loading for build-registered loadables.

Practical consequence:

- dynamic loading is still structurally known to the build
- Polylith can prepare code-splitting and related asset behavior because the loadable graph is declared

## Loadables

Loadables are build-declared modules that can be imported dynamically at runtime.

A loadable can define:

- an entrypoint
- a name used at runtime
- a service prefix for lifecycle startup
- CSS that should load with it

This lets the app defer loading some code while still preserving build-time structural knowledge.

The `player` feature declares a `musicxml-player` loadable for `@music-i18n/musicxml-player`.
The app loads it through `@polylith/loader` only when playback is requested through the `player` registry service.

Important nuance:

- loadables are still built as part of the full app build
- they help runtime loading and watcher scope, not cold full-build cost
- the watcher rebuilds changed inputs, but it should be restarted after build configuration changes such as adding a loadable or copied resource

The player also needs its audio worklet resource copied into the built app.
That is handled through the player feature's `resources` entry for `spessasynth_processor.js`.

Current planning stance:

- do not upgrade the current Polylith builder just to chase newer Rollup behavior during this phase
- Polylith 2.0, which is expected to use newer Rollup and TypeScript support, is the better place to revisit that migration

## Frontend Test Builds

Frontend testing is tightly tied to the Polylith build model.

The UI test lane works because the app build can also define:

- `spec`
  - the test entrypoint
- `testDest`
  - the built test output directory

The flow is:

1. the app build points at the UI test entrypoint
2. Polylith builds the browser test bundle
3. the built output lands under `testDest`
4. Karma runs that built output in the browser

This means frontend tests are not discovered directly from raw source by Karma.
They are assembled by Polylith first.

## Root Spec Aggregation

The root UI test entrypoint is a structural file chosen by the app build.
For the current `mn` app, that file is:

- `src/mn/test.js`

Its job is to aggregate browser specs through explicit imports.
Karma does not discover raw source specs through globs in this setup.

Current `mn` inclusion model:

1. app build chooses `src/mn/test.js`
2. `src/mn/test.js` imports concrete specs or local spec aggregators
3. those imported files may import additional concrete specs

Practical consequence:

- adding a test file is not enough
- the test must be reachable from `src/mn/test.js`
- missing UI specs are usually an import-path problem before they are a Karma problem

Other Polylith apps may use a more layered aggregation path with feature-owned spec entrypoints and synthetic modules.
For `mn`, keep the current rule simple and explicit until there is enough test volume to justify more structure.

## Debugging Build Problems

When something is missing from the built app or test output, check in this order:

1. Is the app build definition including the right feature or entrypoint?
2. Does the feature contribute the right `index`, CSS, resources, or tests?
3. Is the relevant synthetic-module import present, such as `@polylith/features`?
4. Is runtime activation happening after build inclusion?
5. For `mn` UI tests, is the spec explicitly imported from `src/mn/test.js` or from something that file imports?

## Practical Takeaway For Music Notebook

For `music-notebook`, the safest way to think about the build system is:

- the build defines the app
- features contribute into that build
- runtime only works with what the build made available
- frontend tests are built the same way as the app, just from a different entrypoint

That means build decisions are not secondary implementation details.
They are part of the architecture.
